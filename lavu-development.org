#+title: Lavu Development Notes

* Purpose
This file records the design constraints and work log for finishing Lavu:
parser and AST architecture, rewrites/normalization, native evaluation,
the Rust standard library, REPL ergonomics, source diagnostics, and
occurrence typing.

* Language Scope
- Lavu aims to support R5RS: nothing more, nothing less.
- The one intentional future opening is SRFI-9, so user-defined record
  types can eventually appear in inferred types.
- Macros should be expanded before type inference. The type engine does
  not need to infer macro-phase types, but macro expansion must preserve
  source origins so diagnostics point back to user code.

* Implementation Shape
- Prefer a stable AST with reusable traversal over one new AST enum per
  tiny pass.
- Keep the tiny-pass learning style by making each parser, desugar, type,
  or normalization pass small and inspectable.
- The Gerbil wrapper has been removed. Keep the implementation on Lavu's
  native parser, normalizer, type inference engine, evaluator, and
  standard library.
- Preserve source spans and origin metadata through parser, macro
  expansion, rewrites, normalization, type inference, and evaluation.
- Ariadne diagnostics and Reedline highlighting are core design
  constraints, not presentation extras.
- Future REPL stepping should inspect both Scheme rewrites/normalization
  and type inference.

* Parser And AST Direction
The original staged-parser idea was good: each file should demonstrate
one new concept. The current implementation bloated because every new
AST enum requires copying all older variants and all recursive conversion
logic into the next parser file.

The likely replacement shape is:

#+begin_src text
Datum -> SurfaceExpr -> CoreExpr
#+end_src

- =Datum= represents parsed Scheme data: atoms, lists/pairs, vectors,
  quote syntax, quasiquote syntax, and source spans.
- =SurfaceExpr= represents recognized Scheme forms before aggressive
  desugaring: =lambda=, =define=, =if=, =set!=, =begin=, =let= variants,
  =cond=, =case=, =and=, =or=, =do=, =delay=, applications, and literals.
- =CoreExpr= is the smaller evaluator target after derived forms are
  normalized.

Tiny pass files should remain, but they should operate over stable types
with shared traversal helpers instead of defining a fresh enum for every
stage.

Quote handling should distinguish data from expressions. For example,
=Quote(Datum)= is cleaner than =Quote(Expression)= because quoted
program-looking data must not be classified, typechecked, or rewritten as
runtime code.

* Rewrites And Normalization
- Preserve the current educational normalization pipeline, but make each
  rewrite a small pass over stable ASTs.
- Avoid losing source-level shape before diagnostics and type inference.
- Lower derived R5RS forms to a small core only when the next stage
  benefits from that core.
- Future REPL stepping should expose each normalization step.

* Standard Library
- Implement the R5RS standard library in Rust rather than defining most
  procedures in terms of each other.
- Tag each primitive with a runtime implementation and a type scheme.
- Predicate primitives also carry refinement metadata for occurrence
  typing.
- The runtime should support the full numeric tower. Type inference may
  initially treat numeric values coarsely as =number?=, then refine later
  if useful.

* Occurrence Typing
Occurrence typing should use predicate information to refine variables in
control-flow positions.

For example:

#+begin_src scheme
(lambda (x)
  (if (string? x)
      (string-length x)
      (+ x 1)))
#+end_src

The true branch refines =x= to =string?=. The false branch refines =x=
away from =string?=. The final function can infer:

#+begin_src scheme
(-> (U string? number?) number?)
#+end_src

The initial educational model should support:
- Fresh type variables for lambda parameters.
- Constraints from applications of typed primitives and known procedures.
- Union types from branches and compatible constraints.
- Predicate propositions for simple variable tests such as =(string? x)=.
- Refinement propagation through =if=, =cond=, =and=, =or=, and =not=.
- Clear diagnostics when a refinement conflicts with a required type.

Full Typed Racket-style proposition logic is not an initial goal.

* Displayed Type Syntax
The REPL type query syntax is:

#+begin_src scheme
? expr...
#+end_src

Displayed types should resemble R5RS predicate names as closely as
possible. These are displayed type atoms, not runtime predicate calls.
The Lavu REPL can highlight them differently to make that clear.

Core displayed atoms:

#+begin_src scheme
any?
unknown?
never?
unspecified?
boolean?
number?
char?
string?
symbol?
pair?
null?
list?
vector?
procedure?
port?
input-port?
output-port?
eof-object?
#+end_src

Unions:

#+begin_src scheme
(U string? number?)
(U null? (pair? any? any?))
#+end_src

Procedures:

#+begin_src scheme
(-> number? number?)
(-> char? char? boolean?)
(-> string? number?)
#+end_src

Variadic procedures:

#+begin_src scheme
(->* number? number?)
(-> char? char? * boolean?)
(-> string? number? ? string?)
#+end_src

Structured types:

#+begin_src scheme
(listof number?)
(listof any?)
(vectorof number?)
(vectorof any?)
(promiseof number?)
(pair? symbol? number?)
#+end_src

Polymorphic examples:

#+begin_src scheme
(-> (listof a) (listof a))
(-> a (listof a))
(-> (pair? a b) a)
#+end_src

Example REPL output:

#+begin_src scheme
? 1
1 : number?

? "hi"
"hi" : string?

? '(1 2 3)
(1 2 3) : (listof number?)

? (lambda (x) (+ x 1))
#<procedure> : (-> number? number?)

? reverse
#<procedure> : (-> (listof a) (listof a))
#+end_src

=unknown?= means Lavu could not infer a useful type yet.
=unspecified?= is the known R5RS unspecified result produced by mutators
and output procedures. =any?= means any Scheme value is valid.

* Dynamic Features
- =values= should be modeled with expression result types, for example
  one value, many fixed values, or unknown-many values.
- =apply= should eventually use procedure types with fixed and rest
  arguments. A conservative initial type is acceptable.
- =call/cc= should be supported at runtime, but type inference can be
  deliberately approximate. Continuation invocation can initially widen
  to =any?= or behave like =never?= internally when useful.

** Occurrence Typing
- Infer both =if= branches in isolated inference states and merge their
  substitutions, so constraints from one branch do not leak into the
  other.
- Treat =(not (predicate? x))= as a positive refinement for the alternate
  branch.
- Preserve predicate refinements when =and= is used as an =if=
  condition, matching the desugared nested conditional shape.
- Carry multiple simple predicate refinements from an =and= condition,
  so independent facts such as =(string? x)= and =(number? y)= can both
  refine the true branch without adding full proposition logic.
- Infer simple =apply= calls for uniform variadic and rest procedures
  when the final argument has a known list element type.
- Cover =set!= assignment inference so reassignment is checked against
  the existing binding type and mismatches are reported.
- Keep predicate-guarded branch refinements from escaping when the
  opposite branch accepts the unrefined value, so guarded =and= forms do
  not incorrectly require every caller to pass the refined type.
- Future stress targets should cover nested predicate filters such as a
  heterogeneous =process-element= function, sibling refinements through
  =and= over =(pair? x)=, =(number? (car x))=, and =(number? (cdr x))=,
  contradictory paths such as =number?= followed by =string?=, and
  higher-order latent predicate propositions for functions like
  =safe-apply=.
- Add structural predicate refinements for direct =car= and =cdr=
  accesses, so guards such as =(number? (car x))= refine =x= to a pair
  whose corresponding field has the predicate's positive type within
  the guarded branch.
- Extend structural predicate refinements through R5RS composed
  =car=/=cdr= accessors such as =cadr= and =caddr=, so guarded selector
  chains preserve the proven element type in branch results.
- Parse equivalent nested selector spellings such as =(car (cdr x))= as
  the same occurrence-typing path, while still respecting local
  shadowing of accessor names.
- Occurrence-typing stress examples should be kept as concrete
  regressions: the heterogeneous =process-element= shape currently
  exposes the coarse =procedure?= result, sibling =and= refinements need
  pair-field intersection, contradictory =number?=/=string?= paths
  should behave as unreachable =never?= branches, and =safe-apply=
  needs future latent predicate propositions rather than only ordinary
  higher-order procedure constraints.
- Combine repeated branch refinements with a small type intersection
  operation instead of overwriting same-variable facts, so
  =(and (pair? x) (number? (car x)) (number? (cdr x)))= refines =x= to
  a pair with both fields known and contradictory paths stop
  contributing result types.
- Let predicate metadata contain type variables and instantiate them when
  applying occurrence refinements. This is still first-order occurrence
  typing, but it is direct groundwork for future latent predicate
  propositions because predicate facts can now carry fresh result or
  structure variables instead of collapsing to =any?=.
- Add a displayed latent predicate procedure shape
  =(-> any? boolean? : string?)= as the type-level home for propositions
  that say a true result refines the tested value.
- Infer first-order latent predicate parameters from control flow. A
  function like =(lambda (pred proc x) (if (pred x) (proc x) #f))= now
  displays as =(-> (-> any? boolean? : t0) (-> t0 t1) any?
  (U boolean? t1))=.
- Give primitive predicate values latent signatures too, so higher-order
  calls such as =safe-apply= can reject mismatched companion procedures
  like =string?= with =+= before runtime.
- Render latent predicate procedure query blocks with the proposition on
  the result line, for example =-> boolean? : string?=.
- Recognize latent predicate tests in desugared =or= forms, avoiding
  generated temporary names in public inferred types.
- Preserve the first value's inferred type in predicate-aware =or=
  handling, while applying false-branch refinements for =not= conditions.
- Keep latent predicate widening to direct variable operands, so guarded
  selector tests like =(and (pair? x) (pred (car x)))= do not require all
  callers to pass pairs.
- Infer direct lambda applications by binding formals to known argument
  types, preventing lowered =let=, =or=, and =case= binders from leaking
  into public type displays.
- Prefer caller-side type variable names when unifying two unknowns, so
  named =let=, =do=, and local helper parameters do not replace enclosing
  lambda parameter names in displayed types.
- Give constrained numeric and character predicates latent propositions
  too, for example =zero?= as =(-> number? boolean? : number?)= and
  =char-alphabetic?= as =(-> char? boolean? : char?)=.
- Keep latent predicate refinements flowing through simple =apply= calls
  with visible final argument lists, including mismatch diagnostics.
- Recognize simple visible =apply= calls as predicate tests too, so
  =(apply pred (list x))= and =(apply pred x '())= refine like
  =(pred x)= and still display the condition result as =boolean?=.
- Infer simple unary predicate lambdas latently when their body is a

  like =(define stringy? (lambda (x) (string? x)))= refine callers too.
- Extend unary predicate-lambda inference through boolean wrappers such

- Combine same-variable =or= predicate alternatives as union
  propositions, while leaving different-variable disjunctions unrefined.
- Treat boolean wrapper shapes such as =(if (string? x) #t (number? x))=

- Generalize procedure-valued direct lambda argument bindings that still

- Keep the user-supplied occurrence-typing stress examples as direct

  primitive applications, lambdas, definitions, begin, set!, and if.
** First Occurrence Typing
- Add branch-local predicate refinement for simple variable predicates
  such as =(string? x)= and merge branch constraints into union types.
** REPL Type Query
- Add the =? expr...= type query path using the new parser,
  classifier, and inference engine.
- Persist inferred top-level REPL bindings in a session =TypeEnv= so
  later =?= queries can resolve names already evaluated in the REPL.
- Report inference failures discovered during normal REPL evaluation as
  Ariadne type diagnostics while keeping the evaluator dynamic.
- Commit REPL type-environment updates form by form, so successful forms
  remain queryable but a later failed definition does not leak a bad
  inferred binding.
** Native Runtime Seed
- Add a native evaluator on the stable surface AST for literals, quote,
  variables, lambdas, if, begin, set!, define, and a first Rust primitive
  set.
** Derived Form Classifier
- Desugar regular =let=, =and=, and =or= into existing surface core
  forms so type inference and runtime evaluation can share the result.
** Native REPL Evaluation
- Switch the active REPL evaluation path from Gerbil to the native stable
  parser, classifier, and runtime evaluator.
** Gerbil Removal
- Remove the unused Gerbil process wrapper after switching the REPL to
  native evaluation.
** Cond Classifier
- Desugar =cond= clauses into nested =if= expressions on the stable
  surface AST.
** Let Star Classifier
- Desugar =let*= into nested single-binding lambda applications.
** Define Procedure Shorthand
- Support top-level =(define (name args...) body...)= by lowering it to a
  lambda definition.
** Native Numeric Primitives
- Add integer runtime support for subtraction, multiplication, and numeric
  comparison primitives.
** Recursive Native Definitions
- Cover recursive top-level procedure definitions through the native
  evaluator.
- Seed top-level lambda definitions during inference so recursive
  procedure definitions can constrain and call themselves.
** Proper Tail Calls
- Evaluate runtime tail positions through an iterative loop for
  conditionals, body sequences, =letrec= bodies, and procedure calls, so
  tail-recursive Scheme loops no longer consume Rust stack frames.
** Letrec And Named Let
- Classify =letrec= and named =let= on the stable surface path.
- Evaluate local recursive bindings natively with placeholder detection
  for premature variable use.
- Teach inference to seed recursive bindings and infer application of
  locally unknown procedures.
** Case Classifier
- Add =eqv?= primitive metadata/runtime support and lower =case= through
  a single-key lambda application plus nested equality tests.
** Pair And List Primitives
- Add native runtime support for =cons=, =car=, =cdr=, and =append= so
  the evaluator matches the existing standard-library type metadata.
** Dotted List Data
- Extend the stable datum parser and runtime quote conversion to support
  dotted list data without classifying dotted data as expression syntax.
** Numeric Runtime Values
- Represent integer, rational, decimal, and complex literals as native
  numeric values and add exact rational arithmetic for core numeric
  primitives while inference continues to display them as =number?=.
- Accept exact integer-valued rationals and exact complex numbers with
  zero imaginary part for non-negative length/index arguments, so string,
  list, and vector access agree with the runtime's =integer?=
  classification.
** Numeric Promotion
- Promote mixed numeric primitive calls across exact rationals, decimals,
  and complex values while keeping comparisons on real numbers only.
** Do Classifier
- Lower R5RS =do= loops to generated recursive bindings on the stable
  surface path so runtime evaluation and inference reuse =letrec=.
** Delay And Force
- Add =delay= as a surface special form and =force= as a native
  memoizing primitive.
- Add displayed =(promiseof ...)= types so =delay= preserves the delayed
  expression type and =force= returns the promised value type.
** Quasiquote Runtime
- Preserve quote abbreviations as data under quoted data and evaluate
  quasiquote, unquote, and unquote-splicing directly over stable datums.
- Support unquote-splicing in quasiquoted vector templates, sharing the
  same proper-list splice validation used for list templates.
- Infer quasiquote datum shapes like quoted data, while letting
  unquoted expressions and proper-list splices contribute element types
  when their payloads can be classified.
** Quoted Datum Types
- Infer structural types for quoted data, including proper lists,
  dotted pairs, heterogeneous list element unions, and =null?=.
** Predicate Refinement Merge
- Keep predicate refinements branch-local unless the refined branch
  actually mentions the variable, avoiding over-constrained parameters
  for guarded constant branches.
- Preserve predicate-accepted inputs when the opposite branch constrains
  the same variable, so forms like =(if (string? x) #t (+ x 1))= infer
  both accepted parameter cases.
- Recognize the generated single-evaluation =or= shape during inference
  so predicate-first =or= forms can still contribute occurrence-typing
  information without changing runtime lowering.
** Native Diagnostics
- Route native parser, surface, type, and evaluator errors through

  span-oriented failures.

- Keep =append= type metadata conservative because R5RS permits an

** Type Inference Maintenance
- Centralize primitive-specific application inference behind a small
  classifier so new educational special cases do not grow a long
  repeated operator-name chain.
- Instantiate standard-library polymorphic type schemes per use so one
  primitive application cannot leak its element constraints into a later
  use of the same primitive.
- Generalize top-level inferred definitions that still contain free type
  variables, so simple definitions such as identity functions can be used
  polymorphically across later forms.
- Add an optional-argument procedure shape so R5RS procedures with one
  optional port, radix, fill, or second numeric argument reject
  too-many-argument calls during inference instead of looking variadic.
- Accept =null?= wherever a proper =(listof a)= argument is required,
  since the empty list is valid at every proper list element type.
- Classify primitive-specific inference cases through the active type
  environment so lexical bindings can shadow standard names normally.
- Recognize occurrence-typing predicate refinements through the active
  type environment too, including =not=, so shadowed predicate names stay
  ordinary calls.
- Infer callback and thunk result flow through file port combinators and
  =dynamic-wind= instead of collapsing those higher-order results to
  =any?=.
- Give those higher-order combinators polymorphic standard-library
  metadata too, so querying the primitive value shows the callback result
  relationship directly.
- Dispatch primitive-specific inference before inferring the primitive
  operator as a value, avoiding unused fresh type variables in displayed
  results.
- Reject invariant body errors such as =(+ x "hello")= during inference,
  including inside inferred definitions, and avoid committing recursive
  top-level placeholder bindings when inference fails.
- Keep path-sensitive occurrence-typing conflicts in the same category:
  a branch refined to =string?= cannot satisfy a later =number?=
  arithmetic requirement, and this is a hard constraint conflict rather
  than an =unknown?= result.
- In the REPL, infer each top-level form before evaluation so an
  invariant type conflict cannot define a runtime binding.
- Advance REPL macro state datum-by-datum so syntax definitions after a
  failed form do not leak into later interactions.
- Label hard unification failures as type constraint conflicts, reserving
  =unknown?= and =any?= for intentionally coarse inference results.
- Split known R5RS unspecified results from =unknown?=, so mutators,
  output procedures, =load=, and =for-each= infer as =unspecified?=
  instead of pretending inference lost precision.
- Infer omitted =if= alternates and empty generated result sequences such
  as =do= tests with no result expressions as =unspecified?=.
- Normalize collection and port unions in displayed inference results,
  so branch merges prefer shapes like =(listof (U number? string?))=
  over redundant unions with =null?=, multiple =listof= arms, or nested
  =U= forms.
